# ingestion-framework

Metadata-driven ingestion framework that simulates a cloud + Databricks
medallion architecture (bronze/silver) locally, built with PySpark and
Delta Lake.

## 1. Local simulation of the cloud environment

| Real Databricks / cloud concept | Local simulation in this project |
|---|---|
| Spark cluster | `SparkSession.builder.master("local[*]")` (`core/spark_session.py`) |
| Landing zone (ADLS/S3 raw bucket) | `data/landing/<source_subfolder>/` |
| Bronze (Delta table in Unity Catalog) | `data/raw/<table>/` (Delta) |
| Silver (Delta table in Unity Catalog) | `data/std/<table>/` (Delta) |
| Metadata / control tables | `config/metadata/datasets.csv` and `datasets_columns.csv` |
| Databricks Job + parameters (widgets) | `src/jobs_entrypoints/*.py` + CLI arguments |
| Databricks Workflows (orchestration) | Out of scope; the same entrypoints could be called from Airflow/ADF/Workflows unchanged |

Metadata is read from CSV today. The rest of the framework never reads
those files directly, it only knows `MetadataRepository` — that is the
single place to touch if metadata moves to real Delta tables in Unity
Catalog.

## 3. Metadata model

### `datasets`

```
dataset_id;type_origin;subtype_origin;tablename;type_read;type_file;
source_path;raw_path;std_path;type_load;incremental_field;
incremental_mask;partition_field
```

- **type_origin / subtype_origin**: logical source of the data (e.g. `FILE`, `ORACLE`), used by `ReaderFactory` alongside `type_read`.
- **type_read**: read strategy key (`STORAGE_READ`, `JDBC`, `API`) that `ReaderFactory` uses to pick a reader implementation.
- **type_load**: `FULL` or `INCREMENTAL`. Drives both the read strategy (raw and std) and the write mode.
- **incremental_field / incremental_mask**: source column and date/time format used to build the watermark filter, only relevant when `type_load=INCREMENTAL`.
- **partition_field**: physical Delta partition column for `raw` (in source_name space).

### `datasets_columns`

```
dataset_id;column_order;source_name;source_type;dest_name;dest_type;
is_sensitive;is_audit;is_business_key
```

- **column_order**: guarantees a stable column order, independent of the metadata file's row order.
- **is_sensitive**: hashed (SHA-256) at the source -> raw step, never stored in plain text in bronze or silver.
- **is_audit**: generated by the framework (`dt_load`, `ts_load`), not read from the source.
- **is_business_key**: identifies the column(s) used to MERGE (upsert) into std. At least one column per dataset must be flagged when `type_load=INCREMENTAL`, or std writes will fail fast.

## 4. Pipeline flow

### 4.1 source -> raw (bronze) — `SourceToRawJob`

For each `dataset_id`:

1. **Watermark**: if `type_load=INCREMENTAL`, derive the current watermark by reading `raw_path` and taking `MAX(incremental_field)` (see [Incremental strategy](#5-incremental-strategy)). `None` if `raw_path` does not exist yet.
2. **Read**: `ReaderFactory` resolves a reader from `type_read`. `FileReader` reads the source with an explicit schema built from `datasets_columns` (no `inferSchema`), and applies the incremental filter if needed.
3. **Profile**: row count and null counts per column, logged.
4. **Hash**: SHA-256 on `is_sensitive=Y` columns (source_name space — this runs before renaming).
5. **Write**: `RawWriter` writes to `raw_path` in Delta. `FULL` overwrites the table; `INCREMENTAL` appends, physically partitioned by `partition_field` when configured.

Bronze keeps the source's column names and types unchanged (the only
transformation is hashing sensitive values). Renaming, casting and
audit columns are deferred to the next step.

### 4.2 raw -> std (silver) — `RawToStdJob`

For each `dataset_id`:

1. **Watermark**: if `type_load=INCREMENTAL`, derive the current watermark by reading `std_path` and taking `MAX(incremental_field)` — a separate watermark from the one used for raw, since this one tracks progress from raw into std, not from source into raw.
2. **Read**: read `raw_path` (Delta) in full, then filter to rows newer than the std watermark (or read it all, for `FULL` datasets or the first run).
3. **Profile**: same as above.
4. **Select/rename/cast**: `select_and_rename` maps `source_name -> dest_name` and casts to `dest_type`, logging any configured column missing from the source and any source column not mapped in metadata.
5. **Audit columns**: adds `dt_load`/`ts_load` for columns flagged `is_audit=Y`.
6. **Write**: `StdWriter` writes to `std_path` in Delta. `FULL`, or the first run of an `INCREMENTAL` dataset, does a full overwrite (bootstrap). Subsequent `INCREMENTAL` runs do a `MERGE INTO` by `is_business_key` columns: `UPDATE` if the key already exists, `INSERT` otherwise.

## 5. Incremental strategy

The watermark for a layer is **derived on demand**, not persisted in a
separate control table: `incremental.get_current_watermark(spark, path,
dataset, field_name)` reads the layer's own Delta table and returns the
maximum `incremental_field` value already present there (`None` if the
table does not exist yet). If the data is already written, the
watermark already reflects it — there is no separate state that can
drift out of sync with the data, and a job crashing mid-run cannot
corrupt a watermark, because none is stored.

Each layer derives its watermark from its own destination:

- `source_to_raw` compares the source against `MAX(incremental_field)` in `raw_path`.
- `raw_to_std` compares raw against `MAX(incremental_field)` in `std_path` (translated to `dest_name` space, since std has already been renamed).

This is why `std` needs a `MERGE` rather than a plain append: a row
whose `incremental_field` also happens to be its `partition_field` (the
case for `customers`) moves to a new raw partition when it is updated.
A naive append or partition overwrite would leave a stale copy behind
in the old partition; the `MERGE` by business key guarantees a single,
up-to-date row per key regardless of which partition it currently
lives in.

## 6. Design patterns

- **Strategy**: `BaseReader`/`BaseWriter` — the read/write algorithm varies per source/layer without the job knowing about it.
- **Factory**: `ReaderFactory` — decouples "which reader to instantiate" from "how it is used".
- **Template Method**: `BaseJob.run()` fixes the skeleton (`init_config -> process`); each concrete job only implements `process()`.
- **Repository**: `MetadataRepository` — isolates the physical metadata storage from the rest of the system.
- **Metadata-driven / configuration over code**: adding a new dataset requires no code changes, only new rows in `datasets` / `datasets_columns`.

## 7. Running it

Requirements:

```bash
python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Mark `src/` as a sources root (or run with `src/` on `PYTHONPATH`) so
`from framework... import` resolves.

```bash
python src/jobs_entrypoints/run_source_raw.py \
    --job_timestamp 2026-07-10T08:00:00 \
    --environment dev \
    --type_read STORAGE_READ \
    --run_id run_001 \
    --dataset_ids 1,2

python src/jobs_entrypoints/run_raw_std.py \
    --job_timestamp 2026-07-10T08:00:00 \
    --environment dev \
    --type_read STORAGE_READ \
    --run_id run_002 \
    --dataset_ids 1,2
```

`--dataset_ids` accepts a comma-separated list (`1,2`).

## 8. Testing

```bash
python tests/check_pipeline.py
```

A single end-to-end script (no pytest) that builds an isolated
mini-pipeline under `tests/_workspace`, runs both jobs through several
scenarios (initial load, incremental append with a row that changes
partition, idempotent rerun, FULL bootstrap and rerun), and asserts on
row counts, physical partitioning, hashing, and MERGE correctness. It
never touches the project's real `data/`/`config/`.

## 9. Extension points

- **New sources** (real API, direct Oracle/SAP JDBC): implement `BaseReader` and register it in `ReaderFactory`. No changes needed in `jobs/`.
- **Real JDBC**: `readers/jdbc_reader.py` documents the intended implementation (`spark.read.jdbc`, incremental pushdown via `predicates`).
- **Business rules in silver**: `RawToStdJob` can grow additional transformations (deduplication, joins, business rules) without touching `SourceToRawJob`.
